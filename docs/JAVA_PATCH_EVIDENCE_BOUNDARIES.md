# Java Patch 原理与只读识别边界

本文记录本轮对项目现有 Java 修改路径及安装副本静态字节码的复核。只读识别器不会调用 `NetRemover.removeNetValidation`、`supplementPatch`、目标构造器或注册方法；分析副本与输出位于仓库外。文中没有真实注册码、机器标识、敏感配置或厂商二进制。

## 两类指纹必须分开

`LicenseRecoverReadOnlyPatchScanner` 的原版/Patch 双指纹用于证明代码来源和精确版本关系。原始安装包须有可核验来源，对应修改产物须能追溯至同一原版及已审核变换。仅有安装文件、同名备份、历史日志或与现有工具的某个特征相似，都不能建立这条关系。目前未取得这种真实文件对，生产 `REVIEWED` 表继续为空。

Java 三个只读验证器的精确代码集合则用于限定已经人工审核的**当前入口语义**。它们可以证明当前授权入口接受某组条件，不能据此把 `codeIntegrity` 设为 `CONFIRMED_PATCHED` 或证明厂商原生签发。观察哈希不是原版来源证明；语义指纹失配意味着规则不适用，而不是授权无效。

## 独立的当前代码证据通道

`LicenseRecoverReadOnlyJavaScanner.inspect()` 现在同时返回原有授权状态与 `codeEvidence`；原有 `scan()` 仍返回授权状态。两者继续使用一个 Java 扫描入口，组件对照不增加按产品目录名判成功的策略。

代码证据有两个独立维度：

| 字段 | 已接入事实 | 能证明什么 |
| --- | --- | --- |
| `behavior=AUDITED_STATIC_BYPASS` | DS24 完整静态门槛审核通过 | 当前磁盘部署的已审授权门槛静态放行；Patch 来源仍待核 |
| `component=REFERENCE_COMPONENT_MATCH` | J1 注册 JAR 精确匹配用户提供的未修改组件对照 | 仅该组件逐字节相同；不证明整站原版、原生激活或历史 Patch |
| `UNASSESSED` | 输入不适用、未知、变化或无法取得稳定证据 | 没有充分代码证据；不等于未激活或已经修改 |

`authorization` 和 `codeIntegrity` 不因这些代码事实升格。只有独立的完整原生校验可以证明原生有效/无效，只有来源可核验的双指纹才能产生 `CONFIRMED_PATCHED`。普通本地记录接受、备用入口接受、证据文字中出现“静态门槛”均不会产生静态绕过事实。该事实只由生产 `LicenseRecoverReadOnlyJavaVerifier.verify` 的完整正向证明发出，不解析提示字符串猜测。

### J1 用户提供的组件对照

用户说明 YT00123 是从云服务器取得、未做修改的新安装且尚未激活。这是用户说明的来源；本轮没有取得厂商签名安装包，也没有取得同版本原版/Patch 文件对。对照 JAR 的 SHA-256 为 `ef00e4751fcbc5ea6c100e4bbaf73f60094310d26c1894ca3906e70c73f45cfa`。该哈希与来源说明共同限定组件对照，不自动登记为可信整应用原版。

17 份 Java 独立副本重新比对后，14 份使用同一 J1 JAR（含 YT00123）；另外是 DS24 的 J2 与两份 QT30 的 J3。YT00123 与 YT00138 的 278 个依赖 JAR 全部逐字节相同，664 个应用 class 中 662 个相同；授权核心 `Global`、`SysParamInit`、`RegisterUtil` 相同。两个业务 class 的差异不能推断为授权 Patch。其他同 J1 组件的产品仍使用各自实际启动链及本地谓词，不能共享整站结论。

组件通道只认固定 J1 指纹，不因方法名、联网字符串缺失、布尔常量或成功桩认原版/补丁。读取要求唯一的 `ITMCReg*.jar`，并拒绝它与其他依赖 JAR 的同一文件别名，或其他名称 JAR 中存在第二份 `itmc/regedit/RegisterMain.class`。所有路径祖先与文件均检查 `NOFOLLOW_LINKS`，注册组件上限 16 MiB，目录上限 4096 条目；组件内容双哈希以及文件身份、大小、修改时间、目录身份两次一致才采信。

其他 JAR 只经 `NOFOLLOW_LINKS` 通道读取受限 ZIP 中央目录，既不装载类也不解压条目载荷。容器上限 128 MiB，单中央目录上限 4 MiB，单次观察的 ZIP 元数据总预算 64 MiB；损坏、ZIP64、多卷或超限布局保持未知。即使找到早期注册条目，也要完成该中央目录检查后才使用该观察。异常文本不输出配置内容、机器号或未经处理的文件路径。

### 已闭合的 DS24 当前静态门槛

DS24 仍要求 [完整静态证明](JAVA_STATIC_ACCEPTANCE_PROOF.md) 的 329 个应用类、145 个依赖及 61 个启动资源精确匹配，并完成两次稳定读取。全局标志无条件为真、真实监听器跳过原生与产品检查、实际拦截器读取同一标志三者共同构成证据；一个常量类不能替代完整调用链。

组件观察先于静态门槛验证，因此组件读取期间的代码变动会被随后完整门槛证明发现，不在门槛通过后再开启组件读取窗口。最终协调器的输入复核发现变化时，授权结果和代码证据一同撤回。这里证明的是受限部署假设下的当前代码行为，不证明运行中 JVM 的外部共享类路径或内存状态。

目前这批副本支持一份已闭合的当前静态门槛放行证明、14 份用户来源限定的注册组件对照，仍支持零份可信历史原版/Patch 双指纹。显示这些区别是新增证据事实，不是把未知结果改成 Patch。

## 现有 Patch 路径说明了哪些检测盲点

仓库 `NetRemover` 的旧写入路径会修改注册包装入口、原生注册检查及返回信息，并处理受保护 class 与 JAR 内容。其影响超出一个网络调用或布尔返回：应用启动还会读取返回记录、检查产品范围及设置注册/授权标志。因此只找到一个“固定返回成功”的方法，不能证明正在运行的启动入口会经过它，更不能证明后续产品检查接受。

旧写入路径的 `isRmPatched` 以若干网络字符串消失作为重复修改启发式。它没有来源可信的原版对照，也不证明完整控制流。只读扫描明确不使用该启发式来确认 Patch。网络地址被清洗、联网调用缺失或扫描没有报错，都不能成为绿色证据。

本轮没有在真实目录或样本副本上执行这些修改路径来制造绿色样本，也没有把自制变换产物加入真实 Patch 指纹库。

## 已复核的真实入口差异

| 构建范围 | 静态发现 | 对检测器的要求 |
| --- | --- | --- |
| DS24 | 全局两个授权标志初始化为真；实际监听器跳过注册/产品拒绝路径，相应 Struts 拦截器读取同一标志 | 完整应用 class、依赖及真实启动/拦截配置同时绑定；单个全局类不够 |
| XMT0107 | 旧 `RegisterListener.checkReInfo()` 只设置 `hasRegister=true`，但实际 `run()` 调用的是 `checkReInfoNew(String)` | 不能将未被该启动链调用的旧方法认定为有效 Patch；必须审核 New 路径及产品选择 |
| XMT0107 / QT100101 | `RegisterInterceptor.preHandle()` 最后返回 `true`，但此前存在注册、产品授权或数据库页面的 `sendRedirect` | 末尾返回值不等于未拒绝；需分析副作用和每个可达分支 |
| QT100101 | 两参数注册构造器采用注册组件默认的类加载来源路径 | 当前本地记录在 `WEB-INF/lib/config.xml`，不能拿 classes 或 data 下的同名配置替代 |
| QT30103 / QT30104 / XMT0106 | 启动传入 `ServletContext.getRealPath("/")` 给三参数构造器 | 当前本地记录在应用根 `config.xml`；其他位置存在记录不能证明其生效 |
| XMT0107 | `SoftVersionID` 决定构造产品，`regInfo` 与当前 `VersionID` 共同形成实际产品检查集合 | 不能只以目录名或一个产品字符串判定范围；重复/未知元数据结构不得升绿 |
| YT00138 | 启动读取数据库产品信息，继续尝试产品映射、`data/system.json` 与通用产品后备 | 局部配置缺失不能证明所有授权路径均失败；不能执行启动监听器作为只读探针 |

注册组件的 `checkReInfo()` 是反向布尔语义：`true` 表示检查未通过，`false` 表示某条路径接受。三种组件都存在本地、网络或 HASP 分派；本地机器、期限、计次或产品失败不能直接升级为全局“未激活”。有限计次成功分支可能写回计数，错误分支也可能写日志；生产只读识别独立计算已审核的谓词，不执行目标实现。

## 精确代码与启动资源的闭合要求

指纹集合必须涵盖真实入口所在 class、可能覆盖它的 class/JAR，以及审核所依赖的启动和拦截配置。集合增加、删除、改变都要失配；单个 anchor 只用于快速定位候选，不能独自授予接受状态。

需要同时审核 classpath 中的非 class 资源、`META-INF` 容器配置、Spring/Struts 启动参数和外部入口配置。仅封存现有几个 XML、或把整个动态配置排除在外，会漏掉新增 provider、import、loader 或启动选择。动态授权载荷、产品模式和数据库值只能按明确的审核规则处理，并在同次扫描前后复读，不能用更新时间缓存替代内容复核。

检测器证明的是所选磁盘部署及已审核启动规则下的授权入口，不是已经运行进程的内存快照、外部 JVM 参数、容器共享类路径或全部业务健康。发现影响这些假设的未知布局时，应该具体报告不适用原因。

## 必须保留的回归边界

- 相同注册 JAR 配不同监听器、不同构造器路径或不同产品模式不能复用接受结果。
- 未被真实入口调用的成功桩、最后返回 `true` 但仍重定向的方法，不能产生 Patch 或入口接受结论。
- 新增/替换应用 class、依赖、provider、启动资源及运行中输入变化必须撤销原接受结果。
- 本地有效条件可独立证明时允许接受；机器不符、过期、计次不足、缺记录与协议未知只能报告相应局部事实，除非完整无接受后备的拒绝路径已有单独证明。
- 人工审核语义指纹、可信原版/Patch 双指纹和目标原生验证结果必须使用不同证据来源；任一测试不得把它们互相冒充。

实际逐项结果和打包测试以本轮样本报告为准，本文不把测试程序正常退出称为授权验证成功。
