# LicenseRecover v1.2.41

## Java target-native registration parity

- Reworked Java one-click recovery around the selected application's own `ITMCReg*.jar`, `GetRegisterCode` and `RegisterMain` contract instead of treating every Java product as one fixed registration layout.
- Added startup-derived runtime profiles for one-argument default, two-argument path/default, three-argument token/path and target-proven fallback sequences.
- Added path parity for webapp-root, `WEB-INF/classes` classpath-root and registration-component default/CodeSource-derived locations.
- Packed Virbox registration classes are restored only in the isolated helper process; the original application JAR remains untouched and the original registration JAR CodeSource is preserved.
- The helper system classpath remains tool-only. Target `WEB-INF/classes` and `WEB-INF/lib` are loaded through an isolated child-first loader to avoid LicenseRecover compatibility classes shadowing the deployed application.
- Authorization family, concrete startup ProductID and required RegStr tokens are tracked separately. This covers products where `SoftVersionID`, registration family and startup mode token are intentionally different.
- Added support for both direct `getRegStr()` consumers and startup flows that obtain RegStr through `getRegInfo()`/Fastjson, plus RegInfo-only startup profiles where the application itself does not call `checkReInfo()`.

## Final success semantics

Java now follows the same fail-closed rule as the mature .NET path: **writing registration data is not success**.

A one-click Java recovery reports final `OK` only after all of the following complete successfully:

1. Target-native request/authorization generation succeeds.
2. The target `RegisterMain.doRegistry()` call succeeds and does not return `false`.
3. A fresh JVM recreates the target startup-derived constructor/path profile.
4. When the target startup profile uses `checkReInfo()`, it must report registered.
5. `getRegInfo()` must return a non-empty persisted RegStr containing every target-proven required mode token.
6. A non-empty persisted ProName must match the concrete runtime ProductID used by the target startup chain.

Any failure keeps the result non-OK and restores the registration-file snapshot instead of leaving a partially written candidate.

## Regression coverage

The Java regression matrix now covers the observed lineages and invariants from DS50109, DS2406, QT30103, DS2802, DS3110, YT00138, YT00129, QT40101, XMT0102 and XMT0103, together with existing QT100101/YX0305 evidence checks and fail-closed unknown-layout tests.

Notable regressions include:

- DS2802 explicit-root then target-default fallback ordering.
- DS3110 default path derived from the registration component's original CodeSource.
- YT001xx cross-class Servlet-root relay and YT00129's `SoftVersionID != RegStr token` alias case.
- QT40101 classpath-root (`WEB-INF/classes`) and RegInfo-only startup consumption.
- XMT0102/XMT0103 concrete runtime ProductID with Fastjson `regStr` consumption rather than a direct `getRegStr()` call.
- Source-contract guards that prevent the GUI from emitting final success before fresh-JVM verification and prevent the Java host from printing its final `RESULT: OK` before check/RegStr/ProName validation.

The v1.2.41 stable artifacts are published only from a fully successful `main` verification run.

## .NET

The v1.2.40 .NET uppercase-modern-first registration chain and persisted-mode verification remain unchanged.
