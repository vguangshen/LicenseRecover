# YT00123 新安装样本的只读基线审核

审核日期：2026-11-02。用户提供 YT00123 作为刚安装、尚未激活的原版软件，并进一步确认：当前目录本身就是从云服务器下载的原始目录式分发包，下载后没有进行修改，无需再提供单独安装器。按这项来源说明，将首次留存的完整副本及其 SHA-256 清单登记为用户提供、确认未修改的原始分发基线，用于后续同版本差异对照与未激活负向测试。

来源说明与授权判定分别记录：已有原始分发基线不等于已有同版本原版/Patch 成对产物，不能把其他产品的业务代码差异直接认定为授权 Patch。厂商签名或发布校验值没有单独核验；这项边界不否定用户提供的分发来源，也不会把用户确认的未激活状态冒充为扫描器已经独立完成全路径原生验证。

## 样本及比较范围

原安装目录仅作读取、清单和 SHA-256；分析使用仓库外的完整独立副本。副本排除 `.svn`，其余共 3,148 个文件、578,855,924 字节，包括 664 个应用 class 和 278 个直接依赖 JAR。没有运行网站、厂商类、初始化器、注册方法、Patch、网络屏蔽或授权写入；反汇编及分析输出均位于副本输入目录之外。

- 全部 664 个 class 的 major 为 52，证明 Java 8 字节码下限，不证明服务实际 JVM 版本。
- 配置 `global.system.VersionID` 和 `data/config.xml` 的产品标识均为 `YT00123`；该产品号不是已独立证明的厂商发行版本。
- 与原有 YT00138 扫描副本相比，全部 278 个 JAR 相同，664 个应用 class 中 662 个逐字节相同。
- 两个不同 class 是 `com.common.sys.schedule.CommonScheduler` 和 `com.dynamicLoad.PluginService`。前者的全部方法 Code 和属性原字节相同，常量池中的 `syncTaskScore` 调度表达式由每两分钟改为每三十秒，`checkRegister` 注解及注册调用未变；这不是实际调度已经运行的观测。后者的差异集中在业务方法异常日志的调用方式，`getInstance` / `loadJar` / `unloadJar` 的实际结构相同，没有发现新增授权标志、注册判据或反射字段操作。仍保留两套完整构建摘要，不以多数代码相同抹平差异，也不把日志/调度差异认定为授权 Patch。
- `Global`、`SysParamInit`、`RegisterUtil`、`IXmlUtil`、`XssFilter` 等当前注册/启动类与 YT00138 的字节完全相同。
- `WEB-INF/lib/ITMCReg.jar` 是既有 J1 组件，SHA-256 为 `ef00e4751fcbc5ea6c100e4bbaf73f60094310d26c1894ca3906e70c73f45cfa`。组件相同不能证明整个应用处于相同授权状态，也不能证明其他应用是原版或 Patch。

完整代码、JAR 和启动资源的集合摘要用于限定已审核语义，不登记成真实原版/Patch 双指纹。分析中对保护方法体的静态还原没有部署回原安装目录或替换输入样本。

## 生效记录位置与 Register.xml 的真实用途

`SysParamInit.run` 取得 Servlet 根路径，完成初始化步骤后，在 `Global.REGISTER_FLAG` 未置位时调用 `RegisterUtil.checkRegister(root)`。注册工具按产品映射尝试注册器，再检查 `data/system.json` 的平台产品后备，最后尝试通用产品。传给三参数 `RegisterMain` 的路径仍是同一应用根，实际注册读取文件是根 **`config.xml`**。

本次副本中根 `config.xml`、`WEB-INF/lib/config.xml`、`WEB-INF/classes/config.xml` 均不存在，`data/system.json` 也不存在。`data/config.xml` 是应用系统元数据，不能替代根注册记录。

根 `Register.xml` 只有一个没有子节点、属性或文本的 `root` 元素，是 56 字节的空日志 XML 骨架。已审应用 `registerMethod` 在取得注册信息后以 `XMLFiles("Register.xml", root).writeLog(...)` 写入日志；J1 本地、联网等异常路径也会向该文件写日志。因此它不是当前 `regType` / `regName` 授权载荷文件；文件存在、为空、历史写入或含机器信息都不能证明当前有效或无效。

## 不能把缺失直接升级为全局未激活

`XMLFiles.readConfig` 在指定文件不存在时返回空字符串，不会从 `Register.xml` 补取记录。J1 `checkReInfo` 的当前未选择模式分支仍按本地、HASP、联网顺序尝试，而非直接返回拒绝。其联网分支即使用户 ID 为空也会到达 SOAP `checkRegNew`，不能以空记录或空凭据推定服务器必然拒绝。

该 J1 的反向布尔语义是 `false` 表示某条注册路径接受，`true` 才是检查失败。此前还存在基于静态 `updateDate` / `regeditInfo` 的内存缓存接受分支；磁盘文件不存在不能证明一个已经运行的 JVM 没有缓存的接受状态。`Global` 的两个授权标志初始为 `false`，也只是初始化语义，不是对当前运行进程内存的观测。

目标原生流程仍可能查询机器/注册表、联网、访问硬件狗、更新凭据、计次或日志；新提供的未激活样本并未让这些方法变成安全的只读探针。本轮不执行它们。

因此当前可接入的结论是精确构建下的 **`NO_RECORD`：生效本地注册文件缺失，其他授权方式待核**。整体授权仍为未验证，不返回“已激活”“已确认 Patch”或完整入口拒绝。它与用户声明未激活相容，但没有冒充独立证明整个软件未激活。

## 动态装载及回归要求

样本包含动态插件装载能力：`SysLoadPlugJar` 在 ApplicationReady 阶段读取数据库插件信息，在相应软件状态条件成立后，通过 `PluginService_MainPart.loadJar` / `ModuleClassLoader` 进入外部模块，设置 BeanFactory / 线程类加载器并初始化 Bean。该装载框架与 YT00138 的对应 class 相同，但被调用的外部业务插件、数据库状态、容器共享类路径、JVM 参数和当前进程内存不能由顶层 class/JAR 指纹全部替代。本轮没有执行这条链。只能为已审磁盘部署出具本地记录观察，不能据此宣称完整启动或所有业务状态可确定。

新样本应作为生产扫描的负向对照：相同 J1 组件、系统产品配置和日志文件存在不得产生绿色或可信 Patch 结论。检测还须绑定新增构建的完整 class/JAR/资源，覆盖相同 anchor 对应多个完整构建、读取期间文件变化、损坏文件和新配置出现等边界。没有真实原版/Patch 对照时，继续保留来源证明缺口。

公开仓库只保留代码、合成测试和脱敏审核说明；真实厂商二进制、授权/机器字段、数据库配置、原始日志及完整私有清单不提交。
