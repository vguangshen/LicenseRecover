# 应用根目录成套 Patch 指纹与代码证据

2026-11-03。本轮针对“没有绿色 Patch”的反馈复查了扫描路径、真实副本及已有修改工具的原理，没有执行真实注册方法或 Patch。用户随后指出关注 DS0101、DS0105，且目前尚未使用方式三；两项本地授权条件通过不等于发生了代码 Patch。

## 两种检测入口，共享证据模型

Java 与 .NET 仍各有一个公共扫描入口。授权接受、组件代码事实及原版/Patch 完整对照分别报告。绿色是用户选择的共用展示：已审入口通过、独立原生有效或可信 Patch 均可绿色，但标签、`authorization`、`codeIntegrity` 与代码证据不会互相推断。

`LicenseRecoverReadOnlyCodeEvidence` 区分当前静态门槛放行、用户来源限定的注册组件原版对照、严格方法替换候选及未评估。组件结论带应用根相对路径与哈希回执；最终协调器将其与本次 Artifact 观测核对，避免把另一次读取的组件证据拼接进当前结果。静态放行与替换候选均不自动产生 `CONFIRMED_PATCHED`。

## 修复原指纹表的两个盲点

旧表按 `SoftVersionID` 将所有条目合为一个必需集合，无法表达同一产品的多个发行构建或多种 Patch 配方。Java 以 lib 目录作为边界，又无法登记应用 classes 下的修改。

新增 `scanApplication(appRoot, runtime, productMode)`，路径覆盖应用 class、JAR、DLL 和固定启动绑定。编译期 `LicenseRecoverReadOnlyPatchProfile` 分别保存 profile、构建、配方、来源审核引用、固定依赖以及原版/修改目标文件对。产品模式仅用于候选选择，不作为厂商发布版本。

- 每组必须完整匹配固定绑定和全部目标，混合集、缺件或未知目标均不能确认该组。
- 组间是独立替代构建；多个匹配事实有歧义时撤回。多配方仅在同构建、完整原版清单完全相同的情况下合并原版证据。
- 路径、符号链接、目录身份、硬链接、重复记录和 schema 都有检查；两次完整读取的回执变化会撤销结论。
- 指纹记录来自编译目录，不能由目标目录、用户 manifest、备份名或历史操作记录导入。

固定绑定和双指纹目标共同限定该审核配方的范围，不证明全部业务功能可用。512 MiB 限额约束每个 pass 的唯一文件初读；复用 Fingerprint 的目标核对会产生额外读取，两次 pass 的总 I/O 可接近 2 GiB，不应误称整体仅读取 512 MiB。单目录 GUI 时限仍独立生效。

生产真实文件对尚为空；合成测试仅证明检测机制可对已审成套 class/JAR/DLL 产生准确结果，不能当作真实 Patch 命中。

## 当前副本实际能证明什么

Java 17 项中，14 项注册 JAR 与用户说明未修改的 YT00123 对照一致，结论仅限组件。DS2406 的完整代码、依赖和真实监听/拦截链证明静态放行，来源仍未确定。未调用的成功桩、末尾 `return true` 或网络字符串缺失均不用于确认 Patch。详见 [Java 边界](JAVA_PATCH_EVIDENCE_BOUNDARIES.md)。

.NET 10 项的已查当前组件没有匹配所支持的完整替换形态。探测仅支持标准托管 CIL 的完整 bool 常量返回，或严格 `CheckNet(ref local RegeditInfo)` 的声明参数置空并返回 false；要求准确方法归属、签名、实例/静态参数位置及受支持的无 EH/locals 方法体。它是局部候选，初始化器、调用方、依赖和来源仍需审核。复杂永久记录生成、保护器、VM 与其他修改不在此规则内。

因此本轮不会把 DS0101/DS0105 的本地授权成功写成“确认 Patch”，也不会为了绿色伪造指纹。新增代码列、独立 JSON 通道和保留的未确认原因，让授权通过与代码修改状态可以同时查看。
