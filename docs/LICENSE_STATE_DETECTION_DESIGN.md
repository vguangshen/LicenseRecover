# 批量扫描：授权状态只读识别设计

## 原则
状态来源必须是目标软件**当前可重复验证的证据**，不能读取 LicenseRecover 的“曾执行成功”记录来推断当前状态。扫描不得修改授权配置、运行注册写入流程或联网请求。

## 状态与证据

已审核入口通过、已验证激活和已确认 Patch 使用同一个绿色状态「授权可用」，命令行输出 `VERIFIED_USABLE`。旧版正向标签也按此状态识别。完整入口拒绝和扫描异常仍使用各自的状态。

- 原生授权有效需有针对当前产品和机器的独立验证结论。
- 确认代码完整性需对照已知版本的原始文件和经核验的修改。备份、文件时间或网络配置只作为线索。
- 已审核入口通过需有对应构建的完整证据。仅有本地条件通过或其他局部证据时，整体状态仍待核。

## Java
- 使用已识别的运行时注册族与产品标识。
- 仅当已审计的独立 Java Host `verify` 模式能够保证无写入、无联网、无副作用，且能校验当前目标持久化授权时，才可作为有效性证据。
- 当前 `runJavaHost(..., "verify", ...)` 依赖执行流程中已有的 `regStr` 等上下文；不能直接当作独立批量扫描状态接口。
- 无法证明纯只读时，返回“无法验证”。

## .NET
- 现代和旧版使用不同的原生注册/校验接口，不应仅根据 `config.xml` 或 `regName` 存在来判断。
- 解密结构和字段匹配只可证明**本地数据结构一致**，不等于目标软件已认可授权。
- 只读 ABI 元数据探针只能证明接口兼容，不能证明授权有效。
- 原生站点/宿主的只读校验必须先经过副作用审计和独立测试，否则返回“无法验证”。

## Patch 识别
- 维护的是**版本化的原始代码指纹与变更规则**（检测规则），不是“用户曾 Patch 的应用列表”。
- 对每个 DLL/JAR 先确认版本、目标方法与原始基线，再做只读结构比对。
- 不匹配未知版本时必须返回“未知”，不可猜测。
- 同一平台和版本若存在多个经审核的目标文件，必须全部精确匹配同一状态才可确认整套 Patch 或原版。混合原版/Patch、目标缺失、指纹不匹配或重复目标均无法确认整套代码完整性。
- 真实可信指纹集仍为空；模拟文件回归测试仅验证检测器的判定逻辑，不证明任何实际产品已 Patch。

## 批量选择默认行为
- 授权可用：默认不勾选，可人工重新选择。
- 原生校验确认无效：默认勾选。
- 无法验证：默认勾选，但明确显示“未验证”，不得宣称未激活。
- 检测失败：默认不勾选并展示错误。

## 安全与验收
- 对已激活、未激活、仅有配置、仅有备份、未知版本、无权限目录、文件被占用等样本测试。
- 两次连续扫描应返回一致状态；删除 LicenseRecover 历史日志不应改变结果。
- 扫描过程只读；超时可取消；不产生目标目录文件变更。
- 排序与取消勾选不应改变执行对象。
