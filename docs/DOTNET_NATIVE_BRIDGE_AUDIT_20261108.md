# .NET 原生桥接与已有密钥复用审计（2026-11-08）

本轮继续检查 YX030107 同族的小写注册组件，输入限定为 SHA-256 `35e40be423f9ea8493edc29bbdfd406a030309241d6ec8c2f1ae3975ef7e5b5f` 的当前部署副本。所有恢复产物、指令转储和分析回执保存在仓库外；没有执行厂商构造器、原生导出、注册验证、网络或写回方法，也没有修改真实安装目录。以下指纹限定分析对象，不证明厂商原版或历史 Patch 来源。

## 已有密钥分别复用了哪些层

| 已有材料或规则 | 当前用途 | 已取得的证据 |
| --- | --- | --- |
| `virbox_keystream.bin` | 仓库 Java 路径中的受保护 JAR/class 读取，见 `LegacyJavaRegistrationMetadata`、`LicenseRecoverJavaHost`、`NetRemover` 的相关代码 | 它的适用范围来自 Java 保护格式，不能直接套用于 .NET 原生桥接 |
| .NET FOAP 的 RC4 规则 | 复用 `scripts/itmc_foap_unpack_stdlib.py`，恢复当前 DLL 的外层托管方法体 | 小写组件的 323 条 FOAP 记录已恢复作静态分析；对齐填充仅在长度确定、最多三字节且全零时处理 |
| 样本中的原生容器及节密钥规则 | 按当前构建静态转写，在独立目录解开容器并映射各节 | 32 位、64 位原生镜像均已提取，导出表与节边界可解析 |
| 构造器托管解码分支 | 复用已审派生与 RC4 原语，静态恢复选定的构造方法体 | 得到 12 字节头及 80 字节 CIL，并核对长度、类型与元数据引用 |

这些层已经使用现有材料推进，不需要用户提供授权密钥。剩余工作是核实实际分派会选中哪些回调、这些回调如何变换数据，以及后续网站授权门槛。不能用“解出了一份明文”替代全部实际路径的等价性证明。

## 两种原生镜像已完成静态提取

| 架构 | 静态映射镜像 SHA-256 | `vb_onload` 导出 RVA | 已见入口跳转 |
| --- | --- | --- | --- |
| x86 | `ecbd4fd576b0e8497ec0740c85389d19860980a0010f71d74f91c527fe931efe` | `0x1FC0` | `0x1D90` |
| x64 | `3bb2b956c7640f231e95294ae1ecc58d4595dd4465ed393e72695f14f4a57471` | `0x21A0` | `0x1EB0` |

这类容器需要按照恢复后的自定义节描述映射，不能仅以文件开头是否为普通 PE 头判断提取失败。镜像提取没有解决其中所有控制流。

初步反汇编中，多处紧随 `call` 的杂乱字节涉及返回地址调整、栈续址和跳转混淆。纯静态符号跟踪已经解析出多处合法续址，包括 x64 首条相关路径经 122 步到达内存清零操作并继续返回。**杂乱的线性反汇编本身不能证明遇到了另一层加密或缺少密钥。**

目前跟踪仍在部分符号控制目标、指令语义及寄存器局部写入处停止。已解析的路径尚不能构成完整的回调写入清单，也不能证明两种架构的原生行为均等价于托管解码分支。分析只计算已知字节、立即数和符号状态，没有执行提取的机器代码或系统 API。

## 已见条件可达的 JIT 函数指针替换，尚未闭合方法变换

在 YX0302 的 x64 原生镜像中，静态控制流已定位到 `getJit` 名称参数及 `KERNEL32!GetProcAddress` 调用：`0x20EE` 构造名称参数、`0x20F8` 调用导入槽 `0x12040`，随后在 `0x20FE` 保存得到的函数指针。本轮继续解析了 `0x2105` 之后的栈续址分派：非空分支的 `0x228E2 jmp RAX` 目标正是上述查找结果，返回续点为 `0x210C`。

在假设该外部调用返回非空对象的分支中，`0x212F` 调用导入的 `VirtualProtect`，参数包含对象首指针所指地址、长度 8 和保护值 4。`0x2135` 保存原函数指针，`0x2138` 取得本镜像 RVA `0x1DA0`；后续栈运算分派到 `0x22970 XCHG [vtable],RDX`，将该地址写入函数指针槽。`0x215A` 再次调用 `VirtualProtect`，`0x2160` 将原指针保存在全局 RVA `0x1DB80`。最终指针值还经独立、不依赖标志位的代数计算复核。这是条件可达的函数指针替换代码，不能再仅概括为发现名称字符串。

替代函数 `0x1DA0` 从第三参数的 `+0x18`、`+0x10` 读取长度与正文指针，并检查正文后四字节的 `FOAP` 标记。不匹配时经 `0x1E44` 转回保存的原函数；匹配时经 `0x222E3` 进入原生函数 `0x1470`。私有解释器曾在 `0x1542 setne al` 停止；随后补充 SETcc、部分寄存器与位运算标志语义，通过 13 个自编合成用例。这是分析工具支持范围的推进，不是执行提取的机器代码。

继续跟踪可见 24 字节记录迭代、固定长度 RC4 密钥调度/生成、`VBPD` 尾标以及 CIL 头、局部变量和异常区处理。以原生可见常量和独立 RC4 转写做 30 组交叉检查后，lower35 全部 323 条 FOAP 记录的明文字节、尾标及有效 CIL 结构均与既有静态恢复结果相同；其中 153 条只多出已核对的 1–3 字节零对齐。此项证明限定于外层 FOAP 字节一致，不证明内层 VM 钥匙回调或真实 JIT 安装后的全部处理等价。

精确未闭合点包括 CLR 对象布局读取（如 `0x1545/0x154D`、`0x155E/0x1566`）、方法 token 恢复、fallback `0x1150`、分配/复制辅助方法及 `0x19B3..0x1D43` 的局部变量、异常区和次级回调处理。版本全局量 `0x1DBD0` 在早期初始化会被改写，不能把映像中的初始零当作实际运行时版本，进而擅自排除这些路径。

上述外部 API 仅作为静态分析的条件返回边界，没有调用 API、执行提取的机器代码或观察目标进程。因此没有声称本机实际进入了该分支、成功安装钩子，或改写了哪些方法。原生 `0x1470` 的全部变换、回调槽写入集合、x86 对应路径和 YS01 不同原生载荷仍须独立审核，不能据此升级授权状态。

## 可变桥接上下文是具体的未闭合边界

上下文 `02000057` 及其回调子结构 `02000056` 均为 `Sequential`、`Pack=1`。前八字节是大小与标志，其后是七个指针槽。相关委托标注为 `StdCall`、`Ansi`。

| 项目 | x86 | x64 |
| --- | ---: | ---: |
| 上下文大小 | 36 字节 | 64 字节 |
| 回调子结构起点 | `+0x08` | `+0x08` |
| 解密回调 `0400013F` 偏移 | `+0x1C` | `+0x30` |

上述布局还通过自编合成结构在 Windows 两种位数下核对；测试只使用框架和合成类型，没有加载厂商类型。

托管代码中，`06000227@008D` 是解密回调槽的唯一直接赋值，默认目标为 `06000226`。默认回调与托管方法 `0600022E` 使用相同的派生和 RC4 过程，但后续 `0600022A@0106` 调用原生 `vb_onload(ref context, ...)`，传入的是可变上下文。需要继续核对它是否改写上述槽、改写后的函数目标、错误或卸载分支，以及旧回调指针的生命周期。

当前回调由静态上下文持有，原生模块记录也存入静态集合；这只能解释已见的托管引用，不能自行证明原生代码保留的所有指针都始终有效。默认回调等价不代表原生初始化之后的回调也已证明等价。

分派标志来自运行时模块句柄：`GetHINSTANCE == -1` 进入托管文件读取与解码路径，其余情况进入桥接初始化。部署文件的哈希不能单独证明一个运行中站点实际走了哪个模块加载分支。

## 80 字节构造器明文的证明范围

小写 `RegeditInfo` 构造器 `06000082` 经 `06000193` 分派，读取固定构建位置的 92 字节方法体和 16 字节密钥。恢复方法体 SHA-256 为 `e56b2b695cc3b90dd47022360e7917291ca5d507b8ad40724c533b46a1550828`。

托管恢复分支中的 80 字节 CIL 仅设置默认产品、两天前的日期、并发数、天数、空产品范围与班级数，并调用 `Object` 构造器；没有授权验证、文件、注册表或网络操作。局部变量为一个 `System.DateTime`，没有异常处理区。缓存以所属类型与方法索引区分；动态方法生成器将四字节元数据操作数重写为相应运行时 token，保留指令形态，再通过 `DynamicMethod.Invoke` 调用。

不过，构造器路径中的密钥预处理确实会访问桥接回调：

`06000082 → 06000193 → 06000190 → 0600018E → 0600022D`

当原生分支被选中时，`0600022D` 使用当前上下文的 `0400013F` 对该 16 字节密钥进行原地变换。因而，回调改写与变换等价性需要实际闭合；它们不能从这份托管明文中省略。此选定构造路径没有调用另一原生执行器 `06000224`，但仍依赖上述原生密钥处理分支。

## YS01 同族复查与审核范围撤回

YX0102 的 YS01 网站引用另一小写兼容组件，SHA-256 为 `36f58b8657bce75a19356796f21c135104e28f5abc4bc9007f0d4ec517f479df`。本轮从该组件也恢复出同框架的 32/64 位原生容器；其载荷与上述 YX0302 组件逐字节不同，不能继承 YX0302 的回调等价性。

YS01 的 `<Module>` 初始化方法 `06000001` 在 `0x0069` 调用桥接初始化 `06000220(ref context)`，后者包含 `vb_onload` 查找与 `0x00FC` 原生调用。其 x64 原生镜像在 `0x2110` 引用 `getJit` 名称，并于 `0x211A` 经同一导入槽调用 `GetProcAddress`；同样只证明静态查找事实，没有观测实际运行时钩子。

此前“现代授权成功分支不进入小写业务构造器”的证据，尚未覆盖这些模块级初始化及 JIT 路径。Microsoft 的 CLI 规范补充允许模块初始化器调用托管和非托管代码，并将初始化完成保证与首次模块静态字段访问或方法调用关联。本审计没有据此推定调用 `Assembly.Load` 就必然当场执行初始化器，也没有用某个业务构造器尚未进入来排除模块级影响。[Microsoft：Module Initializer](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Ecma-335-Augments.md#module-initializer)

因此，YS01 的审核范围也收紧为现代本地局部条件，并要求精确匹配上述小写依赖；`positiveEntryAudited=false`。当前本地核心判据即使满足，也只能保留 `LocalCondition.SATISFIED`、`Acceptance.UNVERIFIED`，不能沿用完整网站入口通过结论。

v1.2.73 的精确 ZIP 测试回执曾实际记录 19 项入口通过、15 项待核；这是当时扫描器的历史输出。先只撤回 YS01 完整范围时，同一批 34 项样本的状态期望为 **18 项入口通过、16 项待核**。本轮另外补齐的 Java 注册/产品门槛见 [当前 Java 审核](JAVA_CURRENT_LOCAL_AUDIT_20261108.md)，最终汇总以修订产物实际回执为准。原有其他 18 个绿色项的审核范围没有因本次已定位的两类兼容组件而变化；没有用已撤回的 YS01 证明推广到其他组件。

## 完整网站接受证明还需要其他依赖

后续若考虑将该家族升级为完整入口通过，必须同时：

- 按家族精确绑定当前小写组件（YX0302 的 `35e40...`、YS01 的 `36f58...`）及网站、大写注册器、密码、JSON 等已审组件，避免只匹配上位本地协议便沿用整个网站结论。
- 对 x86、x64 实际可达初始化、回调及 JIT 间接目标完成静态审核，核对密钥和方法体来源、原地读写、错误处理、生命周期及作用范围；默认回调或单个托管构造器明文不能排除其余方法和模块受到影响。
- 闭合网站的 `Data/db/RegisterVersion.db` 模式关系读取、解密、父产品选择及当前模式门槛。该查询位于自身产品检查之前，相关异常路径不能直接假设返回空列表。
- 将依赖的文件存在、缺失或内容及扫描期间变化纳入证据。副本没有复制某份数据库，不能据此推定真实站点缺失。
- 用独立只读判据及发布包测试验证全部适用条件，保留原生授权、代码来源与入口接受的不同证据范围。

网站 A/B 的已见入口共性、数据库边界及现代本地条件详见 [YX0302 上位本地审计](DOTNET_YX0302_UPPER_LOCAL_AUDIT.md)。只有当前现代载荷的本地核心条件实际满足时，才报告 `LocalCondition.SATISFIED`、`Acceptance.UNVERIFIED`，保持灰色；其他同族应用继续依据自身记录与适用范围报告。本轮提取和恢复进展没有被转换成原生激活、完整入口接受或确认 Patch。
